# Deployment execution order

1. Sign into AWS with a short-lived identity. Use a trusted Linux host with private access to the EKS API and installed AWS CLI, eksctl, kubectl, Helm, Docker, Trivy and Python 3. A normal public CloudShell session cannot reach a private EKS API; use a VPC CloudShell environment or an in-VPC administration host.
2. Copy infra/deployment.example.json to ignored deployment.json. Fill the region, supported Kubernetes version, repository URL, Route53 domain and hosted zone, Jenkins role, secret name and reviewed chart versions. Select a Gateway API version compatible with the chosen controller. Configuration contains identifiers, not passwords.
3. Review the plan with `python3 scripts/bootstrap.py --config deployment.json --create-cluster --platform-only`. No cloud resource is changed without --apply.
4. Provision the platform with `python3 scripts/bootstrap.py --config deployment.json --create-cluster --platform-only --apply`. The cluster template declares private worker nodes, the managed EBS CSI add-on with its IAM policy, metrics-server, and VPC CNI network policy enforcement. The script installs the ALB controller with dedicated IRSA, the monitoring chart, ECR repositories, and ACM DNS validation. Record the selected versions and infrastructure outputs.
5. Configure Jenkins, SonarQube and TLS Nexus endpoints. Nexus needs both a raw hosted repository and a Docker hosted connector. See nexus.md. Set NEXUS_DOCKER_REGISTRY in the Jenkins parameters. Do not expose administrative interfaces publicly without appropriate authentication and network restrictions.
6. Run the Jenkins checkout, test, analysis, gate, build, scan and publish stages for the first main release. Initial deployment will need the bootstrap to exist before the routine deployment step can succeed. Use the tag from that build in deployment.json; the first bootstrap build may publish successfully and then fail because workloads have not been created yet.
7. Run `python3 scripts/bootstrap.py --config deployment.json --apply` after the images exist. The script reuses or creates the Secrets Manager secret, injects blog-secrets through stdin, renders the manifests, performs a server dry run, applies them, configures the deployer access entry and monitoring, waits for workloads, creates the DNS alias, and runs application read/write validation.
8. Rerun the full Jenkins pipeline. It now performs routine image updates under its namespace Role. Capture both registry references from reports/release.json and the successful pipeline URL.
9. Run `python3 scripts/collect-evidence.py --out evidence` under the administrative identity. The --routine mode used by Jenkins captures only the resources permitted to its deployment Role. It does not require Secret access.
10. Complete the persistence, network isolation, rolling traffic, failed quality gate and failed vulnerability gate demonstrations. Capture genuine browser screenshots for the application, SonarQube, both registries, Jenkins and Grafana. Add the actual URLs and results to the submission record.

For an existing cluster, --create-cluster is omitted. The script verifies its managed add-ons rather than assuming that storage and policy enforcement are available. New cluster provisioning, IAM creation, DNS changes and persistent resources create real account changes and AWS charges. Review the plan and resource lifecycle before execution.
